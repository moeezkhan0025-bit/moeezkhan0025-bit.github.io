SHEET01

Site Development Hub

A web app for land development due diligence, built with Claude Code

THE PROBLEM

On a land development project, the drainage study, environmental assessments, geotechnical report, land plan, traffic study, easements and utility commitments arrive from different consultants over months. Their findings sit in separate PDFs, they contradict each other, and they get revised. The hub pulls every finding out with AI, cites it to the page, flags where reports disagree, tracks revisions and correspondence, and turns the verified results into design guides for the project manager, engineer and designer.

What it does

  • AI extraction against a checklist for each report type, with every quote verified on its cited page
  • Review queue: the engineer verifies or rejects each AI finding
  • Cross-report conflict detection, decisions and action items
  • Revision history, a correspondence log and a project timeline
  • Snapshots that rebuild the project as it stood on any date
  • 15 design guides with drawings and live checks (pipe capacity, weir and orifice, earth balance, traffic tapers) that read the project’s verified values

DESIGN RETRO: WHAT BROKE

The first extraction run split findings too finely (59% strict precision), so I reviewed every extra in the tool and found none were invented, only duplicates and document details. On the larger test, my own validator caught a mistake I made building the data: three findings tagged to pages that didn’t exist in an addendum. And the AI flagged a real checklist answer I had left out of the answer key. Guardrails worked in both directions.

SHEET02

AI tools for site development

Built in-house at Nexco Properties, Houston

THE PROBLEM

Every new site meant rereading the same county drainage manual, cross-checking outside-agency requirements and the company’s own developer agreements, then counting quantities off drawings by hand. That work is expert-heavy, repetitive, and easy to get wrong. I turned it into tools built with LLM agents (Claude Code), each taken from written requirements to a working internal tool.

Design-guide generator

Reads the county drainage manual, outside-agency requirements and in-house developer agreements, then structures those separate sources into one project-specific design guide for each new site. Designers start from one reference instead of working across three separate documents.

Separate sources, one grounded reference per site.

DWG/DWF takeoff estimator

Reads DWG and DWF drawings, pulls quantities from the drawing data, and runs the quantity takeoff for cost estimating, replacing manual counting.

The takeoff runs from the drawing itself.

Drainage design calculators

Weir, channel and flow calculators for day-to-day drainage design, built for the routine hydraulic checks every site needs.

DESIGN RETRO: WHAT BROKE

I scoped a next step that would combine the design guide and the estimator to generate DWG files directly. It ran into file-conversion errors and misread CAD layers, and the output wasn’t reliable. The lesson I took from it: AI is only as good as the data it’s fed, so drawing data needs to be validated and cleaned before anything gets automated on top of it. I documented each failure point as requirements for the next iteration rather than shipping something nobody could trust.

These are internal company tools, so this page describes them without screenshots or company data.

SHEET03

How I deliver AI solutions

Requirements first, staged review, nothing ships unchecked

1. Map the workflow

Sit with the real process first: which documents, which drawings, which decisions take an expert, and where errors creep in.

2. Write the spec

Turn that into written requirements with a clear definition of done, then have agents build to the spec.

3. Review in stages

Review each phase in one pass while the next one builds, then reconcile the two before moving on.
